# 微信小游戏「没声音」排查手册

> **适用场景**：Godot 导出的微信小游戏（`斗战三国小游戏/wxgame/`），音频（BGM / 音效 / 配音）
> 在某处不出声。本文件记录 2026-10-16 那次完整排查的**思路**，供下次遇到同类问题直接照走。
>
> **一句话结论**：Godot Web 胶水搭的 WebAudio 节点链（样本总线 → 混音总线 → destination）
> 在微信里，到扬声器那一段是哑的；把音频源**直接接到 `ctx.destination`** 绕过这条链即可恢复。
> 修复在 `wxgame/game.js` 的 `installAudioBypass()`。

---

## 一、这次是什么问题（结论存档）

### 现象
- 电脑版（`斗战三国/启动斗战三国.command`）音频一切正常
- 微信小游戏里：**BGM、音效、配音全部无声**，但画面 / 逻辑 / 帧率完全正常
- 控制台**不报错**，运行期 0 error —— 典型的「日志全绿但功能异常」

### 根因
Godot Web 胶水的音频输出路径是：

```
音效缓冲(AudioBuffer)
  → BufferSource
  → SampleNodeBus（ChannelSplitter6 → 6×Gain → ChannelMerger6）   ← 样本总线
  → Bus（Gain → Solo → Mute）                                     ← 混音总线
  → AudioContext.destination
```

**这条链在微信里，到 destination 那一步是哑的。**

实测证据：

| 检查项 | 结果 |
|---|---|
| 缓冲里有没有声音数据（RMS） | ✅ 0.088 ~ 0.215，真数据 |
| `start()` 有没有被调用 | ✅ 被调用，`playbackRate=1` |
| 各 GainNode 音量值 | ✅ 全非零（Bus 0.56~1.0，SampleNodeBus 0.079~0.708） |
| 音频上下文状态 | ✅ `48000Hz / running`，没有被挂起 |
| 链尾电平（AnalyserNode 实测） | ✅ **有信号**，0.02~0.05 实时 RMS |
| 把总线出口并联放大 +12dB 再接扬声器 | ❌ **仍然无声** |
| 把 6 声道链路降混成 2 声道 | ❌ **仍然无声** |
| **把音频源直接接 `destination`** | ✅ **全部正常** ← 决定性证据 |

### 修复
`wxgame/game.js` 的 `installAudioBypass()`（约 50 行）：
- hook `AudioContext.prototype.createBufferSource`
- 每个 source 在 `start()` 时**另接一路** `source → GainNode(0.5) → ctx.destination`
- 运行时开关 `g.__dzsgAudioBypass`（增益值，**设 0 即关闭旁路**；只影响之后新建的源）
- **只改 `game.js`，不动 `pkg_engine/index.js`** → 重新从 Godot 导出 Web 包不会丢

### 音量跟随（2026-10-21 补，重要）
最初的 bypass 用**固定增益 0.5**，绕过了 Godot 的混音总线，后果是：
设置里的「音乐音量 / 音效音量」滑条拖到底也没用、BGM 淡入淡出失效、静音关不掉。

现在改成「跟随影子增益」：
1. 在 `AudioContext` 创建的那一刻（以及原型上的 `createGain` /
   `createChannelSplitter` / `createChannelMerger` 等工厂）给节点图记一份连线表；
2. 播放时从音源 BFS 到 `destination`，把路径上所有 `GainNode.gain.value` 乘起来，
   得到 Godot 本来要施加的总音量，塞进旁路的 GainNode；
3. 每 400ms 对仍在播的源重算一次 → 拖滑条 / BGM 淡入 / 静音都即时生效。

**必须用「最大增益路径」而不是最短路径**：Godot 的样本总线是
`splitter → 6 个声道增益(L/R/SL/SR/C/LFE) → merger`，单声道音效只有 L 那路非零。
走最短路径可能先撞上增益为 0 的声道，误判成静音（这个坑踩过）。

- 只有小游戏环境才装旁路（`typeof wx !== 'undefined'`），普通浏览器保持 Godot 原生链路，
  否则会变成双份音量。
- 若微信侧哪天修好了这条链，把 `g.__dzsgAudioBypass` 设为 `0`（或删掉整段）即恢复原生链路。

## 二、下次再遇到「没声音」：照这个顺序查

**总原则：从「数据」到「扬声器」逐层二分；每一轮只改一个变量，只问一个是/否问题。
先用最小实验 + 耳朵缩小范围，再上代码。**

### 第 0 步 · 先分类，别急着翻代码
先问清楚是哪种「没声」：
- **(a) 完全没声** —— 一点声音都没有
- **(b) 部分没声** —— 例如 BGM 有、音效没有
- **(c) 有声但不对** —— 音量过小 / 破音 / 断续

(a) 和 (b) 的查法完全不同。(b) 一般是某类音频走了不同的注册路径。

### 第 1 步 · 分层定位（六层，任何一层断 = 无声）

| 层 | 要验证什么 | 怎么验 |
|---|---|---|
| ① 资源层 | 音频文件有没有打进 pck / 分包 | 解 pck 列文件；看 `game.json` 分包 files 清单 |
| ② 解码层 | `decodeAudioData` 成功吗？缓冲有数据吗？ | hook `decodeAudioData`，读 `getChannelData(0)` 算 RMS |
| ③ 调度层 | `start()` 真被调用吗？速率正常吗？ | hook `createBufferSource`，包住 `start` 打点 |
| ④ 音量层 | 所有 GainNode 值非零吗？ | 收集所有 `createGain` 节点，快照 `gain.value` |
| ⑤ 链路层 | 信号能不能走到 destination？| 在链路各环节挂 `AnalyserNode` 读实时 RMS |
| ⑥ 输出层 | 到了 destination 之后呢？ | **唯一判据：耳朵** |

**关键判断**：如果 ②③④⑤ 全部正常（有数据、有调度、音量非零、链尾有电平）却还是没声，
那么问题一定在 **⑤ 的后半段 / ⑥** —— **不要再回头查数据了**。

### 第 2 步 · 用「绕过法」一刀切开（最有效的一招）
**把音频源直接接到 `ctx.destination`，绕开所有中间节点**：

- 绕过之后**有声** → 问题在中间那条节点链上（本次就是这种）
- 绕过之后**还是没声** → 问题在数据 / 上下文 / 微信输出层，回头查第 1 步的 ①②

代码骨架（**另接一路**，保留原链路不动）：
```js
var origCreate = AudioContext.prototype.createBufferSource;
AudioContext.prototype.createBufferSource = function () {
  var node = origCreate.apply(this, arguments);
  var ctx = this, origStart = node.start;
  node.start = function () {
    var gg = ctx.createGain(); gg.gain.value = 0.5;
    node.connect(gg); gg.connect(ctx.destination);   // 旁路直连
    return origStart.apply(node, arguments);
  };
  return node;
};
```
用「另接一路」而不是「改接」，好处是原链路保持完整，两条路可同时验证，省一半验证轮次。
（代价：若两条路都通了会双重播放、音量偏大，到时把旁路增益设 0 即可。）

### 第 3 步 · 修好后，把探针拆干净
探针（hook / AnalyserNode / 测试音）**一定要拆掉**：
- 日志刷屏会掩盖真实问题
- 探针本身有副作用（本项目踩过：探针 / Proxy 拖累帧率）
- 测试音频文件（如 `audiotest/*.wav`）会被打进主包，白白占配额

## 三、工具箱：本次最管用的几个手法

### 1. 可数听测法（强烈推荐）
让用户配合听时，**不要问「有没有声音」或「比较响还是比较轻」**，歧义太大。改成：

> 「会响 3 组，第 1 组响 **1 声**、第 2 组响 **2 声**、第 3 组响 **3 声**。
>  告诉我你听到了哪几组。」

连续响 N 声 = 第 N 组，用户只需数数，结果离散、可复现。本次就是靠它把范围从"全哑"
缩到"只有游戏自己的音频哑"。

### 2. 探针挂在 prototype 上，绝不碰胶水
`pkg_engine/index.js` 是 Godot 自动生成的，**改了重新导出就没了**。
所有探针都挂在 `AudioContext.prototype.createXxx` 上，写在自己维护的 `game.js` 里。

### 3. AnalyserNode 电平探针
在任意节点后挂 AnalyserNode，周期读 RMS，就知道**信号走到了哪一步**：
```js
var an = ctx.createAnalyser(); an.fftSize = 2048;
someNode.connect(an);
var d = new Float32Array(an.fftSize);
an.getFloatTimeDomainData(d);   // 逐样本平方求和开方 = RMS
```
坑：微信的 `getByteTimeDomainData` 疑似未实现（恒返回 0），**必须用 float 版**。

### 4. 耳朵是唯一终审
探针读数和耳朵可能不一致 —— 本次就是「链尾读得到电平，但扬声器完全没声」。
**探针只能缩小范围，最终判定必须靠听。** 两者缺一不可。

### 5. 别一次改一大堆
17:30 那轮失败的教训：一次塞进大量探针 + 多实例日志互相覆盖，排查效率极低。
**每轮只动一个变量**，一次编译拿一个确定答案。

## 四、已被证伪的假线索（下次直接跳过，别再走一遍）

| 假线索 | 为什么错 |
|---|---|
| 「资源没打包 / 解码失败」 | pck 里 67 个音频齐全，`decodeAudioData` 全成功 |
| 「缓冲是空的 / 静音数据」 | RMS 实测 0.088~0.215，是真数据 |
| 「`start()` 没被调用」 | 打点确认被调用，`playbackRate=1` |
| 「音量被关成 0」 | 所有 gain 节点快照全非零 |
| 「上下文被挂起」 | `state=running`，`48000Hz` |
| **「双声道在微信里播不出声，降混成单声道就行」** | **重大误判**。改完"似乎能听到"就下了结论；后来用**真双声道**测试音验证 —— 照样能听见。**声道数不是原因**。这个修法已撤销（`g.__forceMono` 改回 false） |
| 「把总线音量调大就好」 | 增益 >1（试过 2.38）会让微信音频链输出 **NaN**，反而更坏 |
| 「AudioWorklet 建不起来导致静音」 | 微信 `addModule()` 会**假成功**，且当前基础库 `AudioWorkletNode` 已存在；worklet 只影响播放位置上报，**不是声音通路** |

**一句话**：数据 / 调度 / 音量 / 上下文这四类问题本次全部排除，**别在它们身上浪费时间**。
遇到同类症状，直接从「链路层 + 输出层」入手。

## 五、微信小游戏环境特有的坑（顺手记下）

1. **增益值 > 1 → 整条音频链输出 NaN**。放大音量只能靠**多路并联**（每路 ≤1），不能调大单点增益。
2. **`ctx.audioWorklet.addModule(不存在的文件)` 会假装成功**（宽松实现），不能拿它当能力判据。
3. **`getByteTimeDomainData` 恒返回 0**（疑似未实现），电平检测必须用 `getFloatTimeDomainData`。
4. **启动日志 `dzsg_boot.log` 是同步镜像**，会被宿主重置 / 滞后，不能当唯一真相；
   **IDE 的 Console 面板才是最准的**。
5. **模拟器窗口失焦会暂停游戏**（没日志、没声音），排查时别以为是卡死。
6. **IDE 对工程文件的内容变化会自动重编**（约 3 秒），改完 `game.js` 不用重启 IDE，
   用 `bash _tools/recheck.sh` 读日志即可（`touch` 改 mtime 不触发）。
7. 本机 shell 的 **grep 对中文 / `\|` 交替支持有坑**，检索中文请用工具（ripgrep），
   或脚本里用 `grep -E "a|b"`。

**重新导出 Web 包后必做**（因为 bypass hook 的是胶水里的构造器）：
1. 编译一次，看启动日志有没有这一行：
   `🔊修复: 已启用「音频源直连扬声器」旁路（音量跟随总线，滑条/淡入淡出/静音均生效）`
2. 若没出现 → 胶水的类名 / 结构变了，需要重新确认 hook 的目标（找 `AudioContext.prototype.createBufferSource`）
3. 用**耳朵**确认 BGM + 音效 + 配音三种都在
